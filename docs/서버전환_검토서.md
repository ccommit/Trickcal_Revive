# 트릭컬 포트폴리오 서버 전환 시 DB 설계 위험 요소 검토서

> 작성 기준일: 2026-07-19
> 문서 상태: 검토안 (실제 구현 대상 아님, 향후 서버 전환 시 참고용)
> 검토 대상 문서: `docs/DB_설계서.md`
> 관련 문서: `docs/전체_기획서.md`, `docs/아키텍처_설계서.md`

`DB_설계서.md` §2에 명시된 전제 — "이 프로젝트는 단일 플레이어 클라이언트를 전제로 하며... 멀티 프로필/서버 동기화는 이번 설계 범위 밖이다" — 아래에서 안전하게 성립했던 가정들이, 서버(여러 클라이언트가 동시에 접속하는 실제 백엔드)로 전환하는 순간 깨지는 지점을 찾아 정리했다. 지금 당장 스키마를 고치라는 문서가 아니라, 서버 전환이 실제로 결정될 때 무엇부터 손대야 하는지 미리 표시해두는 체크리스트다.

## 1. 비밀번호를 계정 프로필과 같은 레코드에 평문 저장

**문제**: `account_save.password`가 골드·레벨·닉네임과 같은 레코드 안에 평문으로 들어 있다. 지금은 브라우저 로컬스토리지 하나뿐이라 유출 경로가 사실상 없어서 문제가 안 됐지만, 서버 DB로 옮기면 이 테이블이 그대로 유출됐을 때 비밀번호까지 통째로 새 나간다.

**권장 대응**: 자격증명(`login_id`, `password_hash`, `salt`)을 별도 인증 테이블/서비스로 분리하고, 비밀번호는 bcrypt/argon2 같은 단방향 해시로 저장한다. 게임 프로필 테이블과 인증 테이블은 접근 권한도 분리한다(프로필 조회 권한만으로는 인증 정보에 접근 못 하게).

## 2. `account_id`가 `login_id`와 동일

**문제**: 지금은 "계정 고유 ID = 로그인 아이디"라 모든 자식 테이블(`player_character_save.account_id` 등)이 로그인 아이디를 그대로 참조한다. 나중에 아이디 변경, 소셜 로그인 연동, 탈퇴 후 동일 아이디 재사용 같은 기능이 생기면 로그인 아이디는 바뀌거나 재사용될 수 있는데, 이게 모든 테이블의 외래키라서 연쇄적으로 다 고쳐야 한다.

**권장 대응**: `account_id`는 서버가 발급하는 불변 서로게이트 키(UUID 등)로 분리하고, `login_id`는 `account_id`를 가리키는 별도의 유일 인덱스 컬럼으로 둔다. 로그인 아이디가 바뀌어도 다른 테이블은 전혀 안 건드려도 되게 만든다.

## 3. 아이디 중복 방지가 경쟁 상태에 취약

**문제**: 지금 코드는 "이 아이디가 계정 목록에 있는지 확인 → 없으면 생성"을 순서대로 한다. 자바스크립트 싱글스레드라 안전했다. 서버에서 여러 요청이 동시에 들어오면, 두 요청이 동시에 "이 아이디 없네" 확인하고 둘 다 생성을 시도해 같은 아이디로 계정이 두 개 생기거나 하나가 깨질 수 있다.

**권장 대응**: `login_id` 컬럼에 DB 유니크 제약(unique index/constraint)을 걸어 DB 엔진이 직접 중복을 막게 한다. 애플리케이션 코드의 "확인 후 생성" 로직만으로 유일성을 보장하지 않는다.

## 4. `pending_transaction_id` 단일 필드가 동시 요청을 못 견딤

**문제**: §7 트랜잭션 상태(Prepared→Pending→Committed→Displayed)는 "한 번에 하나의 액션만 진행된다"는 전제로 계정당 필드 하나로 추적한다. 서버에서는 같은 계정으로 두 기기가 동시에 요청을 보내거나, 네트워크 재시도로 같은 요청이 겹쳐 도착할 수 있다. 필드 하나로는 "지금 진행 중인 트랜잭션이 이거 맞나"를 안전하게 판단할 수 없다.

**권장 대응**: 트랜잭션을 계정 레코드의 필드가 아니라 별도의 트랜잭션 로그 테이블(요청마다 고유한 `idempotency_key` 포함)로 분리하고, 계정 잔액 변경에는 낙관적 잠금(버전 필드) 또는 DB 트랜잭션 격리 수준으로 동시 수정 충돌을 막는다.

## 5. 클라이언트가 계산한 결과를 그대로 저장

**문제**: 지금은 전투 승패 판정, 보상 계산, 가챠 결과, 스테이지 클리어까지 전부 클라이언트 자바스크립트가 계산해서 그대로 로컬스토리지에 쓴다. 프로토타입이라 문제 없지만, 서버 환경에서 클라이언트 계산값을 그대로 믿고 저장하면 클라이언트를 조작해 무한 재화·강제 클리어 같은 부정행위가 가능해진다.

**권장 대응**: 보상·가챠·전투 결과처럼 재화/진행도가 바뀌는 판정은 서버가 클라이언트 요청의 입력값(스테이지 ID, 파티 구성 등)만 받아 서버 쪽에서 재계산하고, 클라이언트가 보낸 결과값은 표시 참고용으로만 쓴다.

## 6. 스태미나·일일 초기화가 클라이언트 시각 기준

**문제**: `last_stamina_updated_at`/`last_daily_reset_at`는 "지금 시각과 비교해서 얼마나 지났는지"로 계산되는데, 지금은 클라이언트 기기의 시계가 곧 유일한 기준 시계였다. 서버 환경에서 클라이언트가 보낸 시각을 그대로 믿으면 기기 시계를 조작해 스태미나를 무한정 채우는 것이 가능해진다. 또한 "04:00 초기화"의 기준 시간대(타임존)도 지금 문서에 명시돼 있지 않다.

**권장 대응**: 스태미나 회복량과 일일 초기화 여부는 항상 서버 시각으로만 계산한다. 클라이언트가 보낸 시각 필드는 신뢰하지 않는다. 초기화 기준 시간대(예: KST 04:00 고정)를 문서에 명시한다.

## 7. 세션·동시 기기 로그인 개념 없음

**문제**: 지금 "세션 유지"는 브라우저 로컬스토리지에 마지막 로그인 아이디를 저장해두는 것뿐이라, 애초에 "이 세션이 아직 유효한가"를 검증할 서버가 없다. 서버로 가면 같은 계정으로 PC/모바일 등 여러 기기에서 동시에 로그인하는 상황이 생기는데, 이걸 허용할지, 한쪽을 강제 로그아웃시킬지, 두 기기가 서로 다른 상태를 저장하려 하면 어떻게 할지에 대한 정책이 전혀 없다.

**권장 대응**: 로그인 시 서버가 만료 시간이 있는 세션 토큰을 발급하고, 서버가 토큰 유효성을 검증하도록 바꾼다. 동시 로그인 정책(다중 기기 허용/최근 로그인 기기만 유지 등)을 정하고, 마지막 저장 시각/버전을 비교해 뒤처진 쓰기를 거부하는 충돌 해결 규칙을 추가한다.

## 8. RuntimeData 크래시 감지가 "로컬 파일 존재 여부" 전제

**문제**: §5.2는 "앱 시작 시 `battle_runtime.json` 파일이 남아 있으면 비정상 종료로 간주"하는 방식으로 크래시를 감지한다. 이건 파일이 로컬 디스크에 있다는 전제에서만 성립하는 로직이다. 서버 환경에서 전투 상태는 보통 서버 메모리나 Redis 같은 임시 저장소에 있는데, 여기서는 "앱을 다시 켰다"는 개념 자체가 없고, 대신 "연결이 끊긴 채 일정 시간이 지났다"는 신호로 판단해야 한다.

**권장 대응**: 크래시(비정상 종료) 감지를 "파일 존재 여부"가 아니라 하트비트/타임아웃 기반으로 재설계한다(예: 일정 시간 이상 클라이언트 응답이 없으면 서버가 전투를 강제 종료하고 예약된 자원을 반환).

## 9. 여러 SaveData 파일에 걸친 작업의 원자성 보장 수단 없음

**문제**: 가챠 한 번을 뽑으면 재화 차감(`account_save`) + 사도 획득(`player_character_save`) + 로그 기록(`gacha_log`)까지 서로 다른 "파일"(=서버에서는 서로 다른 테이블)이 함께 바뀐다. 지금은 자바스크립트가 순서대로 실행하니 중간에 끊길 걱정이 적었지만(그마저도 감지 수단은 없다), 서버 DB에서는 이 세 가지 변경 중 일부만 반영되고 나머지는 실패하는 상황(부분 실패)이 실제로 발생할 수 있다.

**권장 대응**: 여러 테이블에 걸친 변경은 실제 DB 트랜잭션(BEGIN/COMMIT/ROLLBACK)으로 묶어 전부 반영되거나 전부 반영되지 않게 한다. §7의 상태 머신은 유지하되, "복구 파일 하나"가 아니라 실제 트랜잭션 로그 테이블(§4 참고)과 DB 트랜잭션을 함께 사용하는 것으로 구현을 바꾼다.

## 10. 스테이지 해금/클리어 판정 주체가 클라이언트

**문제**: `player_progress_save.is_unlocked`/`is_cleared`는 지금 클라이언트가 로컬스토리지를 직접 읽고 쓴다. 서버가 없으니 "이 스테이지가 실제로 해금됐는지"를 검증할 제3자가 없다.

**권장 대응**: 스테이지 진입·보상 지급 요청이 오면 서버가 먼저 `player_progress_save`를 조회해 이전 스테이지 클리어 여부를 검증한 뒤 진입을 허용한다. 클라이언트의 해금 표시는 서버 응답을 반영한 결과로만 취급한다.

## 11. (참고) 스키마 마이그레이션 방식은 그대로 써도 됨

§8의 "파일별 `schema_version` + 단계별 변환 함수 순차 적용" 방식은 로컬 파일이든 서버 DB의 계정별 레코드든 동일하게 적용 가능한 일반적인 지연 마이그레이션(lazy migration) 패턴이다. 서버 전환 시 이 부분은 큰 수정 없이 재사용할 수 있다.
